# Compiler improvement priorities

The [measurements](README.md) distinguish three costs: preparing code for compile-time evaluation, executing that code, and generating optimized application code. The correctness fix makes native reuse safe; the suggestions here are future work.

## Save successful checks' native artifacts

Every cache-enabled command can read native compile-time code, but checking currently discards the native artifacts it generates. Native builds publish reusable packs. This explains the large difference between ordinary warm checks and checks after a dev seed.

The compiler's [cache setup](https://github.com/roc-lang/roc/blob/839d32a335d4273f9ffdf972e9bf2d668cce7b9c/src/cli/main.zig#L251-L298) supplies lookup and splice capabilities; its [evaluator interface](https://github.com/roc-lang/roc/blob/839d32a335d4273f9ffdf972e9bf2d668cce7b9c/src/eval/compile_time_finalization.zig#L53-L100) has no publication interface. [Native-build publication](https://github.com/roc-lang/roc/blob/839d32a335d4273f9ffdf972e9bf2d668cce7b9c/src/cli/main.zig#L11203-L11247) saves eligible artifacts after successful compilation.

Retain and publish the eligible artifacts already generated by checking, without a second compilation. Preserve target, lowering-policy, app-dependency, observation, and provider compatibility. Failed checks must not publish entries that suppress their diagnostics on subsequent runs.

Checking produces only demanded procedures, not necessarily a complete module pack. Use additive, explicitly identified partial-artifact publications; do not let a partial pack occupy an immutable complete-pack path and block later publication.

This is the first recommendation for warm checking and memory. Dev-seeded 0.3-second checks demonstrate potential, not a promised result for a check-only implementation: dev builds may publish additional exported helpers. It will not improve `--no-cache` or eliminate LLVM work.

Validate with a fresh-cache check followed by another check: require actual body-work reduction and identical values, diagnostics, `dbg`, and expect behavior. Include failed checks and app/schema/platform/provider changes.

## Reduce repeated runtime-code expansion

This is the leading direction for faster cold optimized builds and builds after app edits. The repeated-query/row control reduces LLVM's phase from 74.137 to 10.400 seconds while retaining the schema parser and twenty call sites. It does not identify which repeated helpers dominate or isolate row types alone.

Attribute intermediate procedures/statements to source functions and specializations, before and after inlining, ownership analysis, and reachability cleanup. Distinguish genuinely different record construction from representation-independent decoding/traversal machinery.

Where behavior and representation truly match, use an explicit shared helper with varying metadata passed as data, retaining small specialized wrappers for different layouts. Alternatively, improve compiler sharing under complete semantic and layout identities. Similar-looking generated bodies alone do not establish interchangeability.

Smaller intermediate programs can reduce preparation, reference-count processing, LLVM work, and memory in both cold and edited builds. Do not change application semantics or weaken runtime optimization to obtain a smaller benchmark.

## Investigate LLVM's aggregate/local-memory simplification

The sample points toward scalar replacement and memory-to-register promotion. Investigate whether generated aggregate/local-memory and control-flow structure makes LLVM repeatedly reconstruct simpler values. The sample is a ten-second window, not whole-phase attribution.

Collect complete pass times and pre/post-optimization function, block, instruction, and bitcode-size counts. The builder already exposes time reporting but [currently passes `null`](https://github.com/roc-lang/roc/blob/839d32a335d4273f9ffdf972e9bf2d668cce7b9c/src/cli/builder.zig#L751-L775). Attribute large generated functions back to Roc procedures.

Fix a demonstrated representation problem rather than blindly changing LLVM flags. Preserve code quality and the [combined app/builtin optimization boundary](https://github.com/roc-lang/roc/blob/839d32a335d4273f9ffdf972e9bf2d668cce7b9c/src/cli/builder.zig#L618-L668), which allows cross-function inlining and dead-code removal.

## Cache the completed optimized application object

For exact unchanged release builds, the final optimized application object is a useful reusable result. Native dev packs cannot remove LLVM's roughly 74-second stage.

Prefer a whole-application object cache over arbitrary separate module objects that change today's optimization boundary. Key all inputs deciding code: reachable checked program/values, types and app/platform relations, compiler/builtin revisions, target/CPU/features, optimization/inlining policies, debug/PIC/sanitizers, ABI, and static data. Validate object/relocation metadata before linking.

A key available only after lowering saves LLVM time but leaves preparation costs. Avoiding those requires a complete earlier identity, not a source-only approximation. Real app edits normally invalidate the optimized object, so this complements code-sharing improvements; it does not solve cold or edited builds.

## Make cold preparation and ownership analysis cheaper

Cold small LLVM spends 36.442 seconds in shared preparation, including 8.554 seconds specializing, 4.881 seconds generating intermediate code, and 15.827 seconds processing ownership/reference counts. Actual execution is 0.153 seconds.

Cold dev has similar specialization time (8.261 seconds) but much lower intermediate generation (0.343 seconds) and ownership work (0.556 seconds). These are different compiler policies, not evidence that a faster SQL parser would remove the preparation cost.

Identify expanded bodies, repeated graph walks, and emitted ownership variants that cause the difference. Preserve the single shared producer and identical checking observations; do not assume another complete lowering pipeline is cheaper.

Profile live allocations at phase boundaries, separating checked data, specialization/type graphs, intermediate statements/layouts/static data, ownership variants, cache bytes, and LLVM. Peak RSS alone does not identify the owner of memory. Optimize the specific redundant construction or traversal shown by those profiles.

## Recommended order

1. Publish eligible native artifacts from successful checks.
2. Attribute repeated runtime-code expansion and LLVM aggregate-promotion work, then fix the dominant sharing or representation issue.
3. Add exact optimized-object reuse for unchanged release builds.
4. Use allocation and ownership profiles for remaining cold preparation costs.

Caching compiled parser code is valuable, but native compile-time reuse, runtime specialization, and optimized-object reuse have different correctness boundaries. Measure them separately. Do not prioritize a new SQL-result cache, removing checking roots without proof, disabling inlining, or merely increasing thread count over the demonstrated costs.
